Overview

Project Summary

1–2 people per team

Design and build an AI-powered call center intake platform for an international commercial property management firm. Tenants, vendors, and facility managers call in to report maintenance issues, safety incidents, and service requests across a large portfolio of office, medical, industrial, and mixed-use properties.

The system must turn unstructured voice conversations into structured work orders, classify each call into a hierarchical taxonomy (10 top-level categories, 36 subcategories), assign one of four risk levels (LOW · MEDIUM · HIGH · EMERGENCY), and route accordingly. How you compute that risk — score-then-threshold, LLM-judged, rule-based, something else — is a design decision you'll defend. High-risk calls pause for a human reviewer before any action is taken; emergencies trigger immediate dispatch with asynchronous notification.

Beyond the happy path, the platform must handle inarticulate callers, missing information, the need to ask clarifying questions, and situations where the historical record conflicts with what the caller describes. It is evaluated against 1,000 multi-turn transcripts (split into a 200-row labeled dev set for iteration and an 800-row unlabeled test set we use for final grading — exactly like a real benchmark) and a knowledge base of 10,000 historical incident records that your RAG agent retrieves from. The benchmark's case mix is deliberately opaque: expect a realistic spread of routine calls, ambiguous descriptions, calls that need a clarifying question, dead-end unroutable edges, and hazard scenarios designed to tempt an over-reaction. You don't have to run at 10,000 calls/day — but you do have to reason about how your design would hold up there.

The HITL Pipeline

The intake pipeline flows through five stages. The validator gate in stage 4 is where the human-in-the-loop logic lives — the pipeline pauses there when the call is too risky to auto-route.

Stage 4 evaluates each call against risk, not confidence alone. Low confidence is not the same as high risk — Risk = P(error) × Cost(error). A confident classification on a high-severity call may still warrant human review because the cost of a wrong routing decision is catastrophic. A low-confidence classification on a minor issue may not, because the cost of error is negligible. The trigger threshold should reflect both dimensions.

Risk Band What it roughly represents
LOW Routine issue; low cost-of-error; safe to resolve autonomously.
MEDIUM Standard maintenance; still low risk but worth notifying the property manager.
HIGH Significant cost-of-error; a human should probably sign off before you act.
EMERGENCY Life safety or major property risk; dispatch cannot wait on review.

You decide the numeric thresholds that separate these bands and the exact policy for when the validator gate pauses vs. dispatches immediately. Derive both from the provided data — look at intake_risk_level vs. final_risk_level drift in operational/historical_records.json, the was_reclassified / was_over_escalated patterns in evaluation/qa_audit_findings.json, and response-time / cost distributions per subcategory. Justify your choices in the design document. The grader checks band labels and downstream actions; it does not care what numeric cutoffs you used to get there.

Agent contract

Your submission exposes a single callable we can invoke. The batch harness (evaluation/run_eval.py) imports it, runs it over the target transcript file (dev or test), and writes predictions.json. 

def classify(turns: list[dict], caller_phone: str | None) -> dict:
    """
    Args:
        turns:        structured dialogue — [{"speaker": "agent"|"caller", "text": ...}, ...]
                      (flatten it yourself however you like)
        caller_phone: phone number, or None if anonymous

    Returns a dict with:
        category, subcategory, risk_level,
        needs_human_review, needs_clarification,
        building_name, address, floor,
        dispatched_vendor_id, dispatched_emergency_services,
        call_summary,   # 2-3 sentence operator-style narrative
        trainer_log     # {full_transcript, ai_prediction, human_override, final_decision}
    """

While iterating (dev set): python evaluation/run_eval.py --agent my_agent:classify then python evaluation/scoring.py --predictions predictions.json. For final grading, we run the same commands against eval_transcripts_test.json using a held-out answer key — same scoring methodology as your dev run.

Submission

What to Hand In So We Can Grade You

Grading is fully automated. We receive your submission, drop it into a clean Python environment, run the same run_eval.py and scoring.py scripts you've been using, and publish the resulting composite score. For this to work, your repo must hand us three things, in a predictable shape.

1 · Runnable agent module

A Python module that exposes a single callable matching the agent contract above: 

your_submission/
├── agent.py          # def classify(turns, caller_phone) -> dict
├── requirements.txt  # pinned versions of every runtime dep
├── README.md         # how to install + any env vars (e.g. OPENAI_API_KEY)
└── design_doc.pdf    # see item 2

We test with: pip install -r requirements.txt && python evaluation/run_eval.py --agent your_submission.agent:classify --eval evaluation/eval_transcripts_test.json. If that command doesn't produce a valid predictions.json, your score is whatever scoring.py computes on a partial / empty file — which is almost always a fail.

2 · Design document (PDF)
  • Derived policy appendix — your per-subcategory base-risk table, risk-modifier weights, risk-band cutoffs, subcategory→SOP mapping, subcategory→vendor-type mapping, and HITL trigger rule. Show how each was derived (historical aggregation? hand-tuned? LLM-judged?) and justify it.
  • HITL design — graph diagram, exact gate trigger, what the reviewer sees, resume semantics.
  • RAG strategy — what you embed, retrieval parameters, and how you reconcile records the QA team flagged as reclassified or over-escalated (don't just copy the historical label).
  • Vendor-selection tie-breaker — rating? cost? SLA? past performance? — and what you do when nothing qualifies.
  • Trainer-log spec — what your log captures, how you'd replay it to fine-tune the classifier later.
  • Scale thought-experiment — how your design evolves at 10K calls / day.
3 · Sealed & reproducible
  • Determinism — for any given input, classify() should return the same output across runs (within the tolerance of your LLM provider). Pin temperatures, seeds, and model versions.
  • Hard timeout — no single call should take > 30 s; the harness moves on and counts missing fields as wrong. A 1,000-call eval should complete in under 1 hour on a typical laptop.
  • Self-contained — don't read files outside your submission folder. If you build a vector index, ship the built artifact or a build step in the README.
  • Network — you may call OpenAI / Anthropic / local LLM endpoints. Document which.
Transcript batch vs. voice agent — same callable, two front-ends

The grading path is identical for both modes. Everything above applies — one classify() function is the contract. The only difference is how the turns list gets produced before it reaches your agent:

Batch (required)

run_eval.py reads evaluation/eval_transcripts_{dev,test}.json, loops over each row, and calls classify(row["turns"], row["caller_phone"]).

turns is already shaped correctly — the pre-recorded dialogues (200 dev / 800 test) feed straight in.

Voice shell (bonus)

Your STT layer captures the live conversation and accumulates turns into the same [{"speaker": ..., "text": ...}] shape, then hands them to the same classify(). TTS reads back the resulting call_summary or dispatch confirmation.

If your voice loop builds turns in any other shape, wrap it in a thin adapter. Don't fork classify().

Bottom line: build classify() once, score it with the batch harness, and — if you're doing the voice bonus — wrap it behind STT/TTS for the demo. Both modes are graded by the batch harness; the voice shell is a demo-only layer and never the grading channel. This means a working voice demo should require zero changes to your core agent.

What We Grade

Evaluation Axes & Weights

Your composite score is computed by evaluation/scoring.py against your predictions.json. Every axis below contributes to a single score out of 100 — there are no per-axis pass/fail bars to game. Optimize against the weights, not against minimum thresholds.

Composite (out of 100): 15% subcategory · 10% category · 10% risk level · 15% HITL-F1 · 5% clarification-F1 · 10% location fields · 10% vendor match · 10% auto-resolution rate · 5% call_summary · 10% trainer_log.  Hard cost: −5 points for every dispatched_emergency_services=true on a call where the correct action was a routine vendor dispatch.

Axis What it measures Weight
Subcategory accuracy Exact leaf-label match — use the label strings as they appear in the historical records. 15%
Category accuracy Top-level category match (10 categories). 10%
Risk-level accuracy LOW / MEDIUM / HIGH / EMERGENCY band match. 10%
HITL-F1 F1 of needs_human_review against ground truth — pause on the calls that warrant a human, don't pause on the ones that don't. The central HITL skill. 15%
Clarification-F1 F1 of needs_clarification — ask only when genuinely ambiguous. 5%
Location fields building_name + address + floor all match. Caller profiles give defaults; the transcript always wins on conflict. 10%
Vendor match Dispatched vendor satisfies specialty + coverage + certification + SLA + availability. When nothing qualifies, escalate (don't dispatch). 10%
Auto-resolution rate Of the calls labeled as safe to close without a human (LOW risk, no clarification needed, vendor available), what fraction did your agent in fact close? Counterbalances over-cautious routing. 10%
Call summary 2–3 sentence operator-style summary on every prediction. 5%
Trainer log Every call logs AI prediction + final decision + any override. 10%
False-911 hard cost dispatched_emergency_services=true on a call where the right answer was a routine vendor dispatch — these are mixed into the eval set and graded silently. −5 / case
